# /potato-slides — 발표자료 만들기

```
/potato-slides
/potato-slides 10분 발표. 8장 이내
/potato-slides 심사위원용. 결과 먼저, 방법은 뒤에
/potato-slides 랩미팅용. 방법론 자세히
```

> **이 스킬은 요청받았을 때만 실행한다.** `/potato-report` 가 끝났다고 해서 자동으로
> 발표자료를 만들지 않는다. 사용자가 `/potato-slides` 를 부르거나 "발표자료도"라고
> 말했을 때만 만든다. 슬라이드는 대부분의 경우 불필요하고, 만드는 데 시간이 든다.

## 시작하기 전에

`results.md`, `reports/figs/`를 읽는다. **결과가 없으면 만들지 않는다.**

발표 정보를 확인한다. **모르면 반드시 물어본다** — 이 셋에 따라 결과물이
완전히 달라지므로 추측해서 만들면 대개 다시 만들어야 한다:

- **발표 시간** (→ 슬라이드 수를 결정한다)
- **청중** (심사위원 / 교수님 / 기관 담당자 / 팀원)
- **형식** (구두 발표 / 포스터 / 제출용)

## 슬라이드 수 계산

**발표 시간 1분당 1장이 상한이다.** 10분이면 10장, 실제로는 8장이 적당하다.
장표를 늘리는 대신 한 장에 담는 메시지를 줄인다.

## 원칙

### 1. 제목이 곧 결론

```
✗ "실험 결과"
✓ "XGBoost가 베이스라인 대비 정확도 3.1%p 개선"

✗ "데이터 소개"
✓ "부산 청년 18만 건의 주거 이동 기록"
```

제목만 읽어도 발표 내용이 파악되게 만든다.

### 2. 한 장에 메시지 하나

두 개를 말하고 싶으면 두 장으로 나눈다.

### 3. 표는 5행 이내

넘으면 그림으로 바꾸거나 부록으로 보낸다.
발표 중에 아무도 10행짜리 표를 읽지 않는다.

### 4. 마지막 장은 "그래서 무엇을"

한계나 감사 인사로 끝내지 않는다.
이 결과로 **무엇을 할 수 있는지**로 끝낸다.

## 구성 — 청중별

### 해커톤 심사위원 (8장)

```
1. 제목 — 한 줄로 무엇을 했는지
2. 문제 — 왜 이게 문제인가 (숫자로)
3. 접근 — 어떻게 풀었나 (그림 1장)
4. 결과 ★ — 핵심 수치. 가장 크게
5. 검증 — 왜 이 결과를 믿을 수 있나 (감사 결과가 여기 들어간다)
6. 임팩트 — 이게 실제로 쓰이면 무엇이 달라지나
7. 한계와 다음 단계
8. 끝 (연락처/깃허브)
```

심사위원은 방법론을 검증하러 온 게 아니다. **결과를 먼저, 방법은 압축.**
다만 5번(검증)은 빼지 말자 — "그거 과적합 아니냐"는 질문이 반드시 나온다.

### 랩미팅·학술발표 (12~15장)

```
1. 제목
2. 배경 — 선행연구 지형
3. 문제의식 — 무엇이 안 풀렸나
4. 데이터
5-7. 방법 (자세히)
8-11. 결과
12. 해석
13. 한계
14. 다음 단계
```

### 기관·보고회 (10장)

수식과 모델명을 줄이고 **정책적 함의**를 늘린다.
"XGBoost가 0.844"보다 "이 방식으로 대상자를 선별하면 기존 대비 X% 개선"이
훨씬 잘 통한다.

## 만드는 방법 — 두 가지

### 방법 A: python-pptx (기본)

```bash
conda run -n potato pip install python-pptx
```

편집 가능한 `.pptx`가 나온다. 발표 직전에 손보기 좋다.

한글 폰트를 명시한다:
```python
from pptx.util import Pt
run.font.name = '맑은 고딕'   # Windows
run.font.size = Pt(28)
```

**글자 크기 하한** — 뒷자리에서 안 보이면 없는 것과 같다.

| 요소 | 하한 |
| --- | --- |
| 제목 | 30pt |
| 본문 주 불릿 | **24pt** |
| 보조 불릿(들여쓴 것) | **20pt** |
| 표지 부제·날짜 | 18pt |

만든 뒤 **실제로 검사한다.** 눈으로 보지 말고 코드로 세자:

```python
from pptx import Presentation; from pptx.util import Pt
prs = Presentation(path)
bad = [(i, p.font.size.pt, p.text[:30])
       for i, s in enumerate(prs.slides, 1) for sh in s.shapes
       if sh.has_text_frame for p in sh.text_frame.paragraphs
       if p.font.size and p.text.strip() and p.font.size < Pt(20)]
print(bad or "하한 통과")
```

시운전에서 이 검사로 19pt 8건이 걸렸다. 규칙만 적어두고 확인하지 않으면 안 지켜진다.

### 방법 B: Marp (마크다운 → 슬라이드)

마크다운으로 쓰고 변환한다. 버전 관리가 되고 수정이 빠르다.

```bash
npx -y @marp-team/marp-cli slides.md -o slides.pptx
npx -y @marp-team/marp-cli slides.md -o slides.pdf
```

```markdown
---
marp: true
theme: default
---

# XGBoost가 베이스라인 대비 3.1%p 개선

![w:600](figs/model_comparison.png)

5-fold CV, 891건 · 폴드 편차 ±0.018
```

**어느 쪽을 쓸지 물어본다.** 발표 직전 수정이 많을 것 같으면 A,
내용이 자주 바뀌면 B.

## 그림 처리

- 슬라이드용 그림은 **글자를 키워서 다시 그린다.** 보고서용 그림을 그대로
  넣으면 축 라벨이 안 보인다 (`plt.rcParams['font.size'] = 14` 이상)
- 해상도 `dpi=150` 이상
- 배경 투명(`transparent=True`)으로 저장하면 슬라이드 배경과 잘 맞는다

### ⚠️ matplotlib 그림 안에는 이모지를 쓰지 않는다

한글 폰트(맑은 고딕·AppleGothic·나눔고딕)에는 **이모지 글리프가 없다.**
`⚠`, `✓`, `→`, `★` 같은 문자를 `set_title`·`annotate`·`text`에 넣으면
**두부(□)로 깨진다.** 시운전에서 실제로 걸렸다.

```python
ax.set_title("누수 실질적 (⚠ 0.0219)")   # ✗ □ 로 깨짐
ax.set_title("누수 실질적 (* 0.0219)")   # ○ ASCII 로
```

- 강조가 필요하면 **색·굵기·크기**로 한다 (`color="#c0392b"`, `fontweight="bold"`)
- 기호가 꼭 필요하면 ASCII(`*`, `<`, `>`, `-`)를 쓴다
- 마이너스 기호는 `axes.unicode_minus = False` 로 처리한다 (이건 별개 문제)

**마크다운·슬라이드 텍스트 상자에는 이모지를 써도 된다.** 문제가 되는 것은
matplotlib이 폰트로 직접 그리는 경우뿐이다.

**확인법**: 만든 PNG를 실제로 열어본다. 코드만 보고 넘어가면 못 잡는다.

## 발표자 노트

`python-pptx`의 `notes_slide`에 각 장에서 할 말을 넣어준다.
발표 연습에 쓰거나, 다른 사람이 대신 발표할 때 유용하다.

## 저장 위치

`reports/slides-<주제>-<날짜>.pptx`

## 마지막 점검

만든 뒤 이것을 확인해서 알려준다:
- [ ] 슬라이드 수 ≤ 발표 시간(분)
- [ ] 모든 그림에 축 라벨·단위가 있는가
- [ ] 한글이 깨지지 않았는가
- [ ] 수치에 표준편차가 함께 있는가
- [ ] 마지막 장이 "그래서 무엇을"로 끝나는가
