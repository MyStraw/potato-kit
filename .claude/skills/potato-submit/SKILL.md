# /potato-submit — 경진대회 제출

```
/potato-submit
/potato-submit XGBoost 모델로
/potato-submit 점수 0.847 나왔어. 다음에 뭘 해볼까
```

## 절차

### 1. 제출 형식 확인

대회마다 다르다. **`sample_submission.csv`를 반드시 확인한다.**

- 컬럼명·순서
- ID 컬럼의 형식 (문자열인가 정수인가, 0으로 채워진 자리수)
- 예측값 형식 (레이블인가 확률인가, 다중분류면 어떤 형태인가)
- 행 수 (test 행 수와 일치하는가)

**인코딩은 대회에 맞춘다**

| 대회 | 권장 | 이유 |
| --- | --- | --- |
| 캐글·해외 | `encoding="utf-8"` | BOM 없는 순수 UTF-8이 가장 안전 |
| 데이콘·국내 | `encoding="utf-8-sig"` | 한글 컬럼을 엑셀로 열 때 깨지지 않음 |

`utf-8-sig`는 파일 앞에 BOM(`EF BB BF`) 3바이트를 붙인다. **pandas는 BOM을 투명하게
처리하지만 모든 채점기가 pandas를 쓰지는 않는다** — 순진한 `csv.reader`나 일부
업로더는 첫 컬럼명을 `﻿PassengerId`로 읽는다. 한글이 없으면 `utf-8`을 쓰자.

확인법: `xxd sub.csv | head -1` 로 첫 3바이트가 `efbbbf`인지 본다.

### 2. 제출 파일 생성

```python
enc = 'utf-8'   # 캐글·해외 기준. 데이콘 등 한글 컬럼이 있으면 'utf-8-sig' (위 표 참고)
sub = pd.read_csv('data/sample_submission.csv')
sub['target'] = predictions
sub.to_csv(f'submissions/sub_{tag}.csv', index=False, encoding=enc)
```

**생성 후 자동 검증**:
- [ ] 행 수가 sample과 같은가
- [ ] 컬럼명이 정확히 같은가
- [ ] 결측이 없는가
- [ ] 예측값 범위가 맞는가 (확률이면 0~1)
- [ ] ID가 sample과 정확히 일치하는가 (순서 포함)

하나라도 틀리면 제출이 거부되거나 0점 처리된다. 반드시 확인한다.

### 3. 이력 기록 — 이게 핵심

`submissions.md`에 매번 기록한다. **이 기록이 없으면 대회 후반에
무엇이 효과가 있었는지 기억나지 않는다.**

```markdown
| # | 날짜 | 변경점 | CV | LB | 차이 | 파일 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 08-06 | 베이스라인 (LogReg) | 0.8126 | 0.8091 | -0.004 | sub_01.csv |
| 2 | 08-06 | XGBoost | 0.8440 | 0.8402 | -0.004 | sub_02.csv |
| 3 | 08-07 | + Title 피처 | 0.8512 | 0.8398 | **-0.011** | sub_03.csv |
| 4 | 08-07 | + 앙상블 (XGB+LGBM) | 0.8534 | 0.8455 | -0.008 | sub_04.csv |
```

**CV와 LB(리더보드)를 나란히 기록하는 게 핵심이다.**

### 4. CV-LB 괴리 감시 — 가장 중요한 신호

| 상황 | 의미 | 대응 |
| --- | --- | --- |
| CV↑, LB↑ | 정상 | 계속 |
| CV↑, LB↓ | **과적합 또는 누수** | 멈추고 원인 파악 |
| CV와 LB 차이가 일정 | 정상 (분포 차이) | 계속. CV를 믿는다 |
| 차이가 갑자기 벌어짐 | 그 변경이 문제 | 롤백 |

**CV는 오르는데 LB가 떨어지면 거기서 멈춘다.**
점수를 더 올리려 하지 말고 원인부터 찾는다. 대부분 셋 중 하나다:

1. **데이터 누수** — 검증 설계 오류. `methods-reviewer` 호출
2. **CV 과적합** — 같은 폴드로 너무 여러 번 튜닝했다
3. **train/test 분포 차이** — `/potato-eda`의 분포 비교로 확인

이 셋을 해결하지 않고 점수를 올리는 것은 모래 위에 쌓는 것이다.

### 5. 다음 시도 제안

이력을 보고 무엇이 효과가 있었는지 분석해 제안한다.

**일반적인 우선순위** (효과 대비 비용 순):

1. **검증 설계 점검** — 여기가 틀리면 나머지가 다 무의미
2. **피처 엔지니어링** — 대개 모델 튜닝보다 효과가 크다
3. **결측·이상치 처리 방식 변경**
4. **모델 다양화 + 앙상블** — 서로 다른 계열(선형/트리/신경망)을 섞을 때 효과가 크다
5. **하이퍼파라미터 튜닝** — 마지막. 대개 이득이 작다
6. **의사 라벨링(pseudo-labeling)** — 잘 되면 크지만 위험도 크다

**이미 시도한 것을 다시 제안하지 않는다.** `submissions.md`를 먼저 읽는다.

### 6. 제출 횟수 관리

대부분 하루 제출 횟수가 제한된다 (보통 5회).

- 남은 횟수를 확인하고 계획한다
- **CV가 확실히 오른 것만 제출한다.** 감으로 제출하지 않는다
- 대회 마지막에 최종 제출 2개를 고르는 형식이면,
  **CV 최고 하나 + 안정적인 것 하나**로 나누는 게 정석이다

### 7. 최종 제출 전 점검

```
methods-reviewer 로 최종 감사해줘. 누수랑 검증 설계 위주로.
```

**시간이 없어도 이건 한다.** 데이터 누수 하나로 상위권이 실격되는 게 경진대회다.
특히 확인할 것:
- 테스트 데이터가 학습에 들어가지 않았는가
- ID나 인덱스 순서가 타깃과 연관되지 않았는가 (흔한 누수)
- 시계열인데 셔플 분할하지 않았는가

## 산출물

- `submissions/sub_<번호>.csv`
- `submissions.md` — 이력
- `predict.py` — 재실행 가능한 예측 스크립트

## 대회가 끝나면

상위권 솔루션이 공개되면 읽고 `submissions.md` 마지막에 정리해둔다.
"내가 놓친 것"이 다음 대회의 출발점이 된다. 이게 대회에서 얻는 가장 큰 자산이다.
