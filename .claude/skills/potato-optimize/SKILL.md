# /potato-optimize — 최적화·시뮬레이션

```
/potato-optimize 배송 차량 5대로 40개 지점 도는 경로
/potato-optimize 3교대 간호사 근무표. 제약 조건은 ...
/potato-optimize 창구 몇 개면 대기시간 5분 이하가 되나
```

## 이 스킬의 원칙

**최적화의 실패는 대개 푸는 단계가 아니라 세우는 단계에서 일어난다.**
그래서 코드를 짜기 전에 문제를 말로 정리하는 데 시간을 쓴다.

## 절차

### 1. 정식화 — 코드보다 먼저

세 가지를 명시적으로 적는다. 사용자와 확인한다.

```markdown
## 문제 정식화

**결정변수** — 우리가 정할 수 있는 것
  x[i][j] = 차량 i가 지점 j를 방문하는가 (0/1)

**목적함수** — 최소화/최대화할 것
  최소화: 총 이동거리
  (또는: 총 비용, 최대 완료시간, 대기시간 …)

**제약** — 반드시 지켜야 할 것
  1. 모든 지점은 정확히 한 번 방문
  2. 각 차량의 적재량 ≤ 용량
  3. 배송 시간창 준수
  4. 차량은 차고에서 출발해 차고로 복귀
```

**여기서 사용자에게 물어본다**: "빠진 제약이 있나요?"
현장에서 너무 당연해서 아무도 말 안 하는 제약이 반드시 있다
(교대 규칙, 장비 호환성, 안전 규정, 휴게 시간…).

**목적이 여러 개면 짚고 넘어간다.** 비용도 줄이고 시간도 줄이고 싶다면
가중합으로 뭉갤지, 하나를 제약으로 넘길지, 파레토 곡선을 그릴지 정해야 한다.
가중치를 임의로 정하면 그 답의 근거가 사라진다.

### 2. 도구 선택

| 문제 성격 | 도구 |
| --- | --- |
| 선형·정수계획 (자원 배분, 생산 계획) | OR-Tools MIP, PuLP |
| 조합·스케줄링 (근무표, 작업 순서) | **OR-Tools CP-SAT** |
| 차량 경로 (VRP, TSP) | **OR-Tools Routing** |
| 시간에 따라 상태가 변함 (대기행렬, 생산라인) | **SimPy** |
| 네트워크 구조 (최단경로, 최대유량) | NetworkX |
| 연속·비선형 | scipy.optimize |
| 위 방법으로 안 풀리는 큰 문제 | 휴리스틱·메타휴리스틱 (DEAP) |

선택 이유를 한 줄로 말하고 진행한다.

### 2.5 용량 회계 — 솔버를 돌리기 전에 산수부터

**"실행불가(INFEASIBLE)"의 대부분은 솔버가 못 푼 게 아니라 애초에 답이 없는 것이다.**
자원 총량과 수요 총량을 비교하는 산수를 먼저 한다. 30초면 된다.

```python
필요 = 기간 × 시점당_필요량
공급상한 = 인원 × 기간 × (근무가능비율) − 휴가·정비 등 차감
```

시운전 사례: 간호사 12명 / 28일 / 교대당 9명, 주당 최대 5일 근무
→ 필요 252, 공급상한 236. **16슬롯 부족으로 구조적 실행불가.**
솔버를 아무리 돌려도 안 나온다. 인원을 16명으로 올려야 풀린다.

**여유(slack)가 0에 가까우면 경고한다.** 용량이 딱 맞으면 제약 하나만 더 걸려도
깨진다. 같은 시운전에서 5명/3일 케이스는 용량이 정확히 12=12였는데,
"야간 다음날 휴무" 제약 때문에 실행불가가 됐다.

INFEASIBLE 이 나왔을 때의 진단 순서:
1. 용량 회계 — 총량이 부족한가? (부족하면 여기서 끝. 자원을 늘려야 한다)
2. 제약 하나씩 빼보기 — 어느 제약이 범인인지 이분 탐색
3. OR-Tools 라면 `AddAssumption` + `SufficientAssumptionsForInfeasibility()` 로
   충돌하는 제약 집합을 직접 받아볼 수 있다

### 3. 작은 예제로 먼저

**손으로 답을 아는 크기**로 먼저 짠다. 지점 5개, 차량 2대 같은 규모.

이유: 이 단계에서 모델이 틀렸는지 알 수 있다. 큰 문제로 바로 가면
답이 나와도 맞는지 확인할 방법이 없다.

작은 예제에서 **답이 상식과 맞는지** 확인한다. 안 맞으면 모델이 틀린 것이다.

### 4. 실제 규모로 확대

안 풀리면 (시간 초과, 메모리 초과):

- **완화** — 정수 제약을 실수로 풀고 반올림
- **분해** — 큰 문제를 작은 부분문제로 (지역별, 기간별)
- **시간 제한** — 최적해 대신 "좋은 해"로 타협 (`solver.parameters.max_time_in_seconds`)
- **휴리스틱** — 탐욕 알고리즘으로 초기해를 만들고 개선
- **문제 축소** — 명백히 나쁜 선택지를 사전에 제거

**시간 제한을 걸었으면 반드시 밝힌다.** "최적해"와 "30초 안에 찾은 해"는 다르다.

### 5. 민감도 분석 — 생략 금지

**현장 데이터는 부정확하다.** 입력이 흔들리면 답이 얼마나 바뀌는지 봐야 한다.

```python
for perturbation in [0.9, 0.95, 1.0, 1.05, 1.1]:
    # 수요·소요시간 등을 ±10% 흔들어 다시 푼다
    ...
```

- 답이 크게 바뀐다 → 그 최적해는 실무에서 쓸 수 없다.
  강건 최적화(robust optimization)나 여유(buffer)를 넣은 해를 고려한다
- 답이 안정적이다 → 신뢰할 수 있다

**실무에서는 최적해 자체보다 이 분석이 더 중요할 때가 많다.**

### 6. 시뮬레이션의 경우 추가로

- **검증(validation)** — 시뮬레이션 결과를 실제 관측치와 대조한다.
  대조 없는 시뮬레이션 결과는 신뢰할 수 없다
- **난수 반복** — 최소 30회 이상 돌려 신뢰구간을 낸다.
  한 번 돌리고 결론 내리지 않는다
- **워밍업 구간** — 초기 과도 구간을 통계에서 제외한다
- **분포 적합** — 도착·서비스 시간을 실제 데이터로 적합했는가,
  아니면 그냥 지수분포로 가정했는가? 후자면 명시한다

### 7. 결과 정리

```markdown
## 최적화 결과

**문제**: 차량 5대, 지점 40개, 시간창 있음
**도구**: OR-Tools Routing, 시간 제한 60초
**해의 상태**: 실행가능해 (최적성 미증명)

| 지표 | 현재 운영 | 최적화 결과 | 개선 |
| --- | --- | --- | --- |
| 총 이동거리 | 412 km | 337 km | -18.2% |
| 최대 경로 시간 | 6.2 h | 4.8 h | -22.6% |
| 사용 차량 | 5 | 4 | -1 |

**민감도**: 수요 ±10% 변동 시 총 거리 331~349 km (안정적)

**주의**
- 실제 교통 상황 미반영 (직선거리 기준)
- 휴게시간 제약 미포함 → 현장 확인 필요
```
