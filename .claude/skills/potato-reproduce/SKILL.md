# /potato-reproduce — 논문 재현하고 확장하기

```
/potato-reproduce papers/xxx.pdf
/potato-reproduce arXiv:2401.12345
/potato-reproduce <논문 제목> — 저자 깃허브도 찾아줘
```

## 이 스킬의 목표

**"돌아갔다"가 끝이 아니다.** 원 논문의 수치를 재현하고, 안 맞으면 왜 안 맞는지
규명하고, 그 위에서 내 아이디어를 검증할 수 있는 상태를 만드는 것이 목표다.

여기를 대충 넘기면 나중에 "내 아이디어가 좋아서 올라간 건지 세팅이 달라서
올라간 건지" 영영 알 수 없게 된다.

## 절차

### 1. 논문 이해

논문이 PDF면 읽고, DOI/arXiv ID면 받아온다.
`/potato-lit-review`를 먼저 돌려 지형을 파악해두면 좋지만 필수는 아니다.

**정리할 것** (`notes/repro-<논문>.md`):
- 핵심 주장 한 문단
- **재현해야 할 수치** — 어느 표·그림의 어느 숫자인가. 이게 목표점이다
- 사용한 데이터 (공개인가, 어디서 받나)
- 방법 요약 (모델 구조, 학습 설정, 평가 방식)
- 저자가 밝힌 하이퍼파라미터·시드
- 논문에 안 적힌 것 (재현의 걸림돌이 될 부분)

### 2. 저자 코드 확보

- 논문에 깃허브 링크가 있으면 그것
- 없으면 WebSearch로 찾는다 (`paperswithcode`, 저자 이름 + 논문 제목)
- 정말 없으면 논문만 보고 구현해야 한다 → 사용자에게 알리고 진행 여부를 묻는다

```bash
git clone <repo> external/<name>
```

`external/`에 두고 **직접 수정하지 않는다.** 원본을 보존해야 나중에
"원래 코드는 이랬다"를 확인할 수 있다.

### 3. 환경 구성 — 별도 환경에

논문 코드는 대개 옛날 라이브러리를 쓴다. **전용 환경을 판다.**

```bash
conda create -n potato-<이름> python=3.9 -y     # 논문 시기에 맞춰서
conda run -n potato-<이름> pip install -r external/<name>/requirements.txt
```
(환경 이름 규칙은 운영 규칙 4절과 같다: `potato-<프로젝트명>`)

이러면 다른 프로젝트를 망가뜨리지 않는다.

**흔한 문제와 대응**
| 문제 | 대응 |
| --- | --- |
| 버전 고정이 없다 (`requirements.txt`에 `==` 없음) | 논문 발표 시점 기준 버전으로 고정 |
| CUDA 버전이 안 맞는다 | CPU로 먼저 작은 규모 재현. 그다음 GPU |
| 패키지가 사라졌다 | 대체 패키지 찾기, 또는 해당 부분만 직접 구현 |
| Python 버전이 너무 옛날 | 3.8~3.9로. 문법 오류가 나면 최소 수정 |
| **macOS에서 `Library not loaded: @rpath/libomp.dylib`** | `conda install -c conda-forge llvm-openmp` |

> `libomp` 문제는 macOS 전용이다. LightGBM·XGBoost가 OpenMP 런타임을 요구하는데
> macOS에는 기본 탑재돼 있지 않다. **Windows·Linux에서는 발생하지 않는다.**
> 시운전에서 LightGBM이 이것 때문에 죽었고, conda 한 줄로 해결됐다.

### 4. 원 논문 결과 재현 — 목표점

**저자가 쓴 데이터로, 저자 설정 그대로 돌린다.** 여기서 내 데이터를 쓰면 안 된다.

```markdown
## 재현 결과

| 항목 | 논문 값 | 재현 값 | 차이 | 판정 |
| --- | --- | --- | --- | --- |
| Table 2 AUROC | 0.847 | 0.843 | -0.004 | ✅ 오차 범위 |
| Table 2 F1 | 0.712 | 0.681 | -0.031 | ⚠️ 확인 필요 |
```

**수치가 안 맞으면 원인을 규명한다.** 흔한 원인 순서대로:

1. **시드** — 저자 시드를 썼는가. 여러 시드로 돌려 분산을 본다
2. **데이터 버전** — 데이터셋이 그 사이 갱신됐는가
3. **전처리 차이** — 논문에 안 적힌 전처리가 코드에 있는가 (또는 반대)
4. **분할 방식** — 논문과 코드의 분할이 다른 경우가 흔하다
5. **평가 방식** — 마이크로/매크로 평균, 임계값 설정
6. **라이브러리 버전** — 기본값이 바뀐 경우 (특히 sklearn)

원인을 못 찾아도 **차이를 기록하고 넘어간다.** 다만 "이 차이를 안고 시작한다"는
것을 명시한다. 나중 결과 해석에 영향을 준다.

### 5. 내 데이터에 적용 — 어댑터를 만든다

**저자 코드를 뜯어고치지 않는다.** 대신 내 데이터를 저자 코드가 기대하는
형태로 바꾸는 층을 만든다.

```
adapters/
└── my_data_adapter.py    # 내 데이터 → 저자 코드가 기대하는 입력 형식
```

이유: 저자 코드를 고치면 원본과 비교가 안 되고, 논문 업데이트를 반영할 수 없다.

**저자 코드가 내 데이터를 거부하는 것은 정상이다.** 논문 벤치마크 데이터는 대개
정제돼 있어서, 실제 데이터의 결측·희귀범주·형 불일치를 상정하지 않는다.
시운전에서도 첫 실행이 `NaN values in continuous columns are currently not allowed!`
로 죽었다 (Age 결측 177건).

흔한 거부 사유와 어댑터 쪽 대응:

| 저자 코드가 거부하는 것 | 어댑터에서 |
| --- | --- |
| 결측값 | **폴드 내부에서** 대치. 전체 데이터로 대치하면 누수다 |
| 문자열 범주형 | `category` dtype 으로 변환하거나 인코딩 |
| 클래스 라벨이 0..K-1 이 아님 | `LabelEncoder` 로 재매핑, 예측 후 역매핑 |
| 컬럼 순서·이름 | 저자가 기대하는 순서로 재배열 |
| 데이터 규모 (너무 작음/큼) | 그대로 보고. 억지로 맞추면 결과가 무의미해진다 |

> ⚠️ **대치를 폴드 밖에서 하지 말 것.** 저자 API가 `fit(X, y)` 형태라 파이프라인에
> 못 넣는 경우가 있는데, 그때는 CV 루프 안에서 **학습 폴드 통계로만** 대치하고
> 검증 폴드에 적용한다. 편해 보인다고 전체 데이터에 미리 대치하면 그 순간
> 재현 실험 전체가 무효가 된다.

**먼저 데이터 특성 차이를 짚는다.**

```markdown
## 데이터 차이

| 항목 | 논문 데이터 | 우리 데이터 | 영향 |
| --- | --- | --- | --- |
| 규모 | 50만 건 | 3만 건 | 과적합 위험 ↑ |
| 클래스 비율 | 1:1 | 1:9 | 불균형 처리 필요 |
| 피처 수 | 128 | 87 | 일부 피처 부재 |
| 관측 주기 | 1시간 | 1일 | 시간 해상도 낮음 |

→ 원 논문 성능이 그대로 나올 것으로 기대하면 안 된다
```

이 표를 안 만들고 진행하면, 성능이 안 나올 때 "내가 잘못한 건지 데이터가
다른 건지" 구분이 안 된다.

### 6. 아이디어 확장 — 한 번에 하나씩

내 아이디어를 얹을 때는 **변경점을 하나씩 추가하고 각각의 기여를 따로 측정한다**
(ablation study).

```markdown
| 설정 | 성능 | 기여 |
| --- | --- | --- |
| 원 논문 방법 (우리 데이터) | 0.782 | 기준 |
| + 변경 A | 0.795 | +0.013 |
| + 변경 B | 0.791 | +0.009 |
| + A와 B 함께 | 0.803 | +0.021 |
```

한 번에 여러 개를 바꾸면 무엇이 효과가 있었는지 모른다.

**감사를 잊지 않는다** — `methods-reviewer`로 확장한 부분을 검토한다.
원 논문에 없던 누수를 내가 만들었을 수 있다.

### 7. 재현 리포트

`reports/reproduction-<논문>.md`:

```
1. 논문 요약과 재현 목표
2. 환경 (Python·라이브러리 버전, 하드웨어)
3. 재현 결과 대조표 + 차이의 원인
4. 데이터 차이 분석
5. 우리 데이터 적용 결과
6. 확장 실험 (ablation)
7. 결론 — 재현 가능성 평가 + 우리 문제에 대한 시사점
부록: 실행 방법 (누가 봐도 다시 돌릴 수 있게)
```

## 데이터 보호

논문 데이터가 공개여도 **내 데이터는 제한이 있을 수 있다.**
의료·임상 데이터라면 `CLAUDE.md`의 데이터 보호 규칙이 그대로 적용된다 —
원본 레코드는 로컬에서만, 모델에는 스키마와 집계만.

## 재현이 실패했을 때

실패도 결과다. 다음을 기록하면 그 자체로 가치가 있다:

- 어디까지 됐고 어디서 막혔는가
- 무엇을 시도했는가
- 논문에 없어서 추측해야 했던 부분
- 저자에게 물어봐야 할 것 (이메일로 문의하는 것은 흔한 일이다)

**"재현 불가"는 학계에서 보고할 가치가 있는 발견이다.** 숨기지 말자.
