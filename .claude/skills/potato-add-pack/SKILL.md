# /potato-add-pack — 전공 팩 관리

전공별 MCP 서버·파이썬 패키지·감사 체크리스트를 묶어 켜고 끈다.

## 사용법

```
/potato-add-pack list              팩 목록 보기
/potato-add-pack <이름>             팩 켜기
/potato-add-pack remove <이름>      팩 끄기
/potato-add-pack new <분야>         새 팩 만들기
/potato-add-pack status            지금 켜져 있는 것 확인
```

## 팩 정의 파일 위치

순서대로 찾는다:
1. `~/.claude/packs/*.md` (설치된 위치)
2. `./.claude/packs/*.md` (킷 폴더에서 작업 중일 때)

찾지 못하면 사용자에게 potato-kit 설치 여부를 확인한다.

---

## `list` — 목록 보기

팩 파일들의 frontmatter(`name`, `title`, `domain`)를 읽어 표로 보여준다.
이미 켜져 있는 팩은 표시한다 (`claude mcp list` 결과와 대조).

```markdown
| 팩 | 분야 | 상태 |
| --- | --- | --- |
| medical | 의료·약학·바이오 | ✅ 켜짐 |
| finance | 금융·시계열 | — |
...

새 분야가 필요하면: /potato-add-pack new <분야이름>
```

## `<이름>` — 팩 켜기

### 절차

1. **팩 파일을 읽는다.** 없으면 비슷한 이름을 제안한다.

2. **사용자에게 무엇을 할지 먼저 보여준다.**
   - 설치할 MCP 서버 목록 (검증 상태 ✅/⚠️ 포함)
   - 설치할 파이썬 패키지
   - 필요한 API 키가 있으면 어디서 받는지
   - 예상 소요 시간

   **⚠️미검증 항목이 있으면 반드시 알린다.** "이건 확인 안 된 명령이라
   실패할 수 있는데, 실패하면 대안을 찾아드리겠다"고 미리 말한다.

3. **확인을 받는다.** 설치는 시스템을 바꾸는 일이므로 사용자 승인 없이 진행하지 않는다.

4. **환경을 준비한다.** 이미 있으면 만들지 않는다:
   ```bash
   conda env list | grep -q '^potato ' || conda create -n potato python=3.11 -y
   ```

5. **파이썬 패키지를 먼저 설치한다.**
   ```bash
   conda run -n potato pip install <패키지들>
   ```

6. **MCP 서버를 등록한다.** 반드시 `-s user` 스코프로 — 그래야 어느 폴더에서든 쓴다.
   ```bash
   claude mcp add -s user <이름> -- <명령>
   ```

   API 키가 필요하면 `-e KEY=value`로 넘긴다:
   ```bash
   claude mcp add -s user fred -e FRED_API_KEY=xxx -- <명령>
   ```

   **키가 없으면 여기서 멈추고 사용자에게 발급을 요청한다.**
   발급 URL을 보여주고, 받아오면 이어서 진행한다.

7. **미검증 항목은 설치 전에 확인한다.**
   - PyPI 패키지: `conda run -n potato pip index versions <패키지>` 또는 그냥 설치 시도
   - npm 패키지: `npm view <패키지> version`
   - 실패하면 → WebSearch로 현재 올바른 패키지명·저장소를 찾는다
   - 그래도 안 되면 → 팩 파일의 "파이썬 패키지" 대안으로 안내하고,
     REST API 직접 호출 헬퍼를 만들어줄 수 있다고 제안한다

8. **연결을 확인한다.**
   ```bash
   claude mcp list
   ```

9. **결과를 보고한다.**
   ```markdown
   ## medical 팩 설치 완료

   ✅ 붙은 것
   - biomcp — PubMed, 임상시험, 유전자변이, OpenFDA
   - lifelines, scikit-survival, tableone (파이썬)

   ⚠️ 실패한 것
   - (있으면 무엇이 왜 실패했는지, 대안이 무엇인지)

   ### 새로 켜진 감사 항목
   methods-reviewer 가 이제 의료 특유의 함정도 본다:
   표본 선택 편향, 결측 메커니즘, 불멸 시간 편향, 임상적 유의성 등

   ### 바로 해볼 것
   /potato-lit-review <관심 주제>

   **Claude Code를 껐다 켜야 MCP가 반영된다.**
   ```

10. **재시작을 안내한다.** MCP는 세션 시작 시 연결되므로 재시작이 필요하다.

---

## `remove <이름>` — 팩 끄기

```bash
claude mcp remove <서버이름>
```

파이썬 패키지는 지우지 않는다 (다른 데서 쓸 수 있고, 지워봐야 이득이 없다).
지워달라고 하면 그때 지운다.

끄는 이유를 짧게 확인한다 — 안 써서인지, 오류가 나서인지.
오류 때문이면 고칠 수 있는지 먼저 본다.

---

## `status` — 현재 상태

```bash
claude mcp list
conda env list
```

켜진 MCP를 팩 정의와 대조해 "어떤 팩이 켜져 있는지"로 번역해 보여준다.
어느 팩에도 속하지 않는 MCP가 있으면 따로 표시한다.

## `new <분야>` — 새 팩 만들기

목록에 없는 전공을 위해 팩 파일을 새로 만든다.

### 절차

1. **분야를 구체화한다.** "화학"만으로는 부족하다. 무슨 데이터를 다루고
   무엇을 하려는지 물어본다. 이미 알 수 있으면 묻지 않고 진행한다.

2. **조사한다.** WebSearch로:
   - 그 분야의 주요 공개 데이터베이스
   - 해당 DB의 MCP 서버 존재 여부 (github, npm, PyPI)
   - 없으면 REST API나 파이썬 클라이언트 라이브러리
   - 그 분야에서 흔한 방법론적 함정 (감사 체크리스트 재료)

3. **`.claude/packs/README.md`의 형식**에 맞춰 팩 파일을 쓴다.
   - 실제로 확인한 것만 ✅, 나머지는 ⚠️
   - **감사 체크리스트를 반드시 채운다.** 이게 팩의 진짜 가치다.
     MCP는 대체될 수 있어도 이 지식은 남는다
   - 데이터 소스 메모에 **국내 소스**도 찾아 넣는다

4. **저장 위치**: `~/.claude/packs/<이름>.md`
   (킷 폴더에서 작업 중이면 `./.claude/packs/`에도 복사해 원본에 남긴다)

5. 만든 뒤 바로 켤지 물어본다.

### 새 팩을 만들 때의 원칙

- **조회는 MCP, 계산은 코드.** 최적화·시뮬레이션 라이브러리를 MCP로 감싸려 하지 않는다
- **한 팩은 한 전공.** 여러 분야를 밀어 넣으면 안 쓰는 도구가 컨텍스트를 먹는다
- **없으면 없다고 쓴다.** 존재하지 않는 MCP 서버를 지어내지 않는다.
  대신 파이썬 라이브러리와 REST API로 대안을 만든다

---

## 주의

- MCP 등록은 항상 `-s user` (유저 스코프). 프로젝트 스코프로 넣으면
  그 폴더에서만 동작한다
- 팩을 여러 개 켜면 도구 수가 늘어 컨텍스트를 먹는다.
  안 쓰는 팩은 끄라고 권한다
- 설치 실패는 흔한 일이다. 실패를 숨기지 말고 정확히 무엇이 왜 실패했는지 보고한다
